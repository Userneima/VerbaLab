# VerbaLab 产品卡点 / 断点 / 功能缺漏测试方案

日期：2026-04-28  
目标：用一张可执行的优先级表，系统找出当前产品里会阻断用户完成学习闭环的卡点、断点和功能缺漏。

## 测试重点

当前最高风险不在“功能数量不够”，而在这些链路是否真的闭合：

- 小程序核心闭环：表达指导、保存、资产可见、词卡创建、词卡复习、删除。
- 账号与同步：微信绑定、账号密码登录、小程序与 Web 双端数据一致。
- AI 服务：返回是否贴合输入、失败是否明确暴露、授权和 CORS 是否稳定。
- 学习资产管理：语料、词卡、卡壳点是否可搜索、可删除、可复习、刷新后仍存在。

优先级定义：

| 优先级 | 判定标准 |
| --- | --- |
| P0 | 用户无法完成核心价值、数据丢失、登录 / 同步失败、安全或成本风险 |
| P1 | 功能能用但明显卡顿、绕路、状态不一致、学习效果受损 |
| P2 | 信息架构、视觉、文案、低频功能缺漏，影响长期体验但不阻断主流程 |

## P0 测试表

| ID | 测试链路 | 要找的问题 | 关键测试场景 | 通过标准 |
| --- | --- | --- | --- | --- |
| P0-01 | 小程序：表达指导 | AI 是否真的基于输入生成，是否出现无关 fallback | 输入“我们不是一路人”“我被这个项目压住了”等中文，连续生成 3 次 | 返回内容与输入强相关；失败时明确报错，不展示无关建议 |
| P0-02 | 小程序：表达保存到资产 | 保存后是否立即可见，不依赖手动同步 | 生成表达指导 -> 保存例句 / 自改句 -> 切到资产页 | 资产页无需点“同步资产”即可看到新卡壳点 |
| P0-03 | 小程序：未登录保存 | 用户是否知道为什么不能保存、下一步做什么 | 匿名状态生成表达后点击保存 | 弹窗提示需要登录 / 绑定；不在按钮下方隐蔽显示；不丢当前生成结果 |
| P0-04 | 小程序：账号密码登录 | Web 账号是否可在小程序登录 | 用已知 Web 邮箱密码登录；用错误密码登录 | 正确账号能登录并同步；错误密码显示中文可理解错误，不显示原始英文报错 |
| P0-05 | 小程序：微信绑定 + 邀请码 | 新用户是否能完成绑定，邀请码失败是否清楚 | 未绑定微信登录；有效邀请码；无效邀请码；已使用邀请码 | 首次无邀请码提示需要邀请码；有效码成功；无效 / 已用统一提示 |
| P0-06 | 小程序：词卡创建 | 工坊是否能生成并保存词卡 | 输入 `stiff`、`mirage`、短语 `follow up` 创建词卡 | 有预览、有语体解析、有例句；保存后进入资产词卡列表 |
| P0-07 | 小程序：词卡复习 | 复习是否包含检验阶段，结果是否持久化 | 打开词卡详情弹窗 -> 句子重排 -> 记住了 / 还不熟 | 未完成重排时不能点“记住了”；完成后更新 `reviewStage / nextDueAt`；退出重进仍保留 |
| P0-08 | 小程序：删除资产 | 卡壳点 / 词卡是否真的可删，是否会被同步复活 | 删除卡壳点和词卡 -> 重新进入资产页 -> 手动同步 -> 重开小程序 | 删除项不再出现；不会被云端旧数据复活 |
| P0-09 | Web + 小程序同步 | 两端数据是否一致 | 小程序保存卡壳点 / 词卡 -> Web 同步查看；Web 创建词卡 -> 小程序同步查看 | 两端数量和关键字段一致，尤其词卡复习状态一致 |
| P0-10 | AI 授权与 CORS | 线上 / 小程序是否出现 Unauthorized / Failed to Fetch | Vercel、微信开发者工具、手机预览分别调用 AI | 需要登录的接口带 token；匿名接口只用于表达指导；无 CORS / 合法域名错误 |
| P0-11 | 本地优先与刷新 | 刷新 / 重开后学习资产是否丢失 | 保存表达、词卡、复习结果后关闭重开小程序和 Web | 本地数据仍在；网络失败不清空本地资产 |
| P0-12 | 管理员 / 邀请码后台 | 普通用户是否能越权访问 | 普通账号访问 `/admin`、邀请码接口；管理员访问 | 普通用户被拒绝；管理员可用；邀请码库存不会缓存到非管理员环境 |

| ID | 测试链路 | 要找的问题 | 关键测试场景 | 通过标准 |
| --- | --- | --- | --- | --- |
| P1-01 | 小程序资产信息架构 | 表达 / 卡壳 / 词卡是否混乱 | 连续保存 10 条卡壳点、10 张词卡 | 资产页仍可搜索、排序、删除、打开详情，不显得堆满 |
| P1-02 | 小程序搜索 | 搜索框是否可用、字号 / 高度是否合理 | 搜中文、英文、搭配、词卡 headword | 14px 左右视觉正常；搜索框不预留大空白；结果准确过滤 |
| P1-03 | 小程序词卡排序 | 词卡多了后是否可管理 | 按待复习、首字母、添加时间切换 | 排序稳定；待复习优先符合 `nextDueAt`；不会改变真实数据 |
| P1-04 | 小程序词卡详情弹窗 | 信息是否过载或遮挡 | 打开长语体解析、长例句词卡 | 弹窗可滚动；按钮始终可见；关闭后列表状态不丢 |
| P1-05 | 小程序卡壳点压缩展示 | 卡壳点是否太占高度 | 保存短句、长中文、无推荐表达三类卡壳点 | 列表只展示中文 + 推荐表达 + 简短预览；详情弹窗展示完整内容 |
| P1-06 | Web 词卡生成质量 | AI 解析是否仍“讲废话” | 生成 `mirage`、`originative`、`perpetuate`、常用词 | 有原词定位、分档替换、例句对比、避坑、目标搭配；不返回空壳 |
| P1-07 | Web 错题库 | 是否强化正确句而非错误句 | 新增错误句 -> 补全正确句 -> 刷新 -> 展开详情 | 正确句主显示；错误句弱化；正确句持久化 |
| P1-08 | Web 实验室 | 降难度是否可逆、是否仍训练输出 | 正常造句 -> 降一级中文提示 -> 再降一级词块重排 -> 回到上一级 | 降难度可逆；不直接给完整答案作为主流程 |
| P1-09 | Web 实战仓 | 长输出支架是否不喂答案 | 回答题目失败后降低难度 | 提供中文骨架 / 关键句重排，不直接生成整段可提交答案 |
| P1-10 | Web 语料库 | 语料是否可搜索、编辑、删除、复用 | 从实验室 / 卡壳点保存语料后管理 | 来源清楚；编辑删除有效；跳转 / 高亮不失效 |
| P1-11 | AI 使用量后台 | token 记录与异常冻结是否可信 | 管理员查看用量；模拟高频请求 | 成功 / 失败 AI 请求都有记录；触发阈值后 429；管理员可解冻 |
| P1-12 | 产品事件埋点 | 指标是否回答产品问题 | 完成表达、保存卡壳、创建词卡、复习词卡 | 后台能看到事件；不保存完整用户输入或 prompt 原文 |

## 执行顺序

1. 先跑自动化基线：`npm run typecheck`、`npm run test`、`npm run build`、`npm run build:weapp --prefix apps/weapp`。
2. 再测 P0 小程序闭环：表达生成 -> 保存 -> 资产可见 -> 登录 -> 同步 -> 删除 -> 重开。
3. 再测 P0 Web / 小程序跨端同步：重点看删除是否复活、词卡复习状态是否一致。
4. 再测 P0 AI / API：匿名接口、登录接口、CORS、合法域名、Unauthorized、429。
5. P0 全部通过后，再进入 P1 的体验和学习效果测试。
6. P2 放在体验版发布前集中检查。

## 验收口径

- P0 全部通过，才可以认为“小程序内测核心闭环可用”。
- P1 中如果出现“功能存在但用户必须绕路”的问题，优先转成下一轮产品修复任务。
- P2 主要服务发布体验和长期可维护性，不应抢占 P0 数据可靠性问题的处理优先级。

## Assumptions

- 本方案同时覆盖 Web 与微信小程序，但当前优先级偏向小程序，因为它最近改动最多且自动化覆盖最薄。
- “卡点”按用户无法理解下一步或需要绕路操作判断。
- “断点”按流程中断、数据丢失、登录 / 同步失败、AI 无法返回判断。
- “功能缺漏”按长期学习资产缺少删除、编辑、搜索、排序、复习、同步反馈等必要控制判断。
- 本方案是测试设计，不直接修改代码；执行测试后应把 P0 / P1 问题转成可修复 issue 或下一轮实现任务。
